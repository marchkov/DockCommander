# DockCommander — актуальный план

Обновлено 20 ноября 2026. Версия: 0.2.1; базовый HEAD: `12d9b1c`, исправления запуска, очереди и CI в рабочем дереве.
Это текущий план. `CODEX_TASK.md` сохраняет исходные требования MVP.
Статус удалённых Actions и опубликованных релизов в этой проверке не проверялся.

После добавления системного меню (20 ноября): 122 теста; Windows — 121 успешный,
Ubuntu WSL — 120 успешных, без ошибок. Пропущены проверки чужой платформы
(корзина и, на Linux, Windows Shell). Проверено создание настоящего Shell-меню;
живой Shift+клик и выполнение команд расширений остаются для ручной проверки.
Причина прежних 22 сбоев: проверка готовности H: занимала около 6 секунд, превышая
ожидание UI-тестов. Загрузка мест перенесена в фон после открытия сохранённых папок;
тесты изолированы от дисков хоста. Добавлены проверки медленной загрузки и закрытия окна.

## Уже реализовано

- Две панели, темы, собственные заголовки, диалоги с Enter/Esc.
- Файловые операции, конфликты, просмотр F3, внешний редактор F4, переименование.
- Маски выделения, Alt+F1/F2, компактные места Linux и меню переполнения.
- Внутреннее перетаскивание и внешнее копирование из системного файлового менеджера.
- Windows: Shift+правая кнопка открывает классическое системное меню файлов,
  выделения или фона папки. При непустой очереди оно блокируется; Linux без изменений.
- Прогресс текущего файла и всей операции, подсчёт, отмена.
- Очередь копирования/перемещения: одна операция выполняется, остальные ожидают;
  панели доступны, ожидающие задания можно убрать. Delete/rename/mkdir при непустой
  очереди отклоняются с сообщением, а не автоматически ставятся в очередь.
- Корзина Windows и Linux/GIO, отдельное подтверждение безвозвратного удаления.
- Копирование и пофайловое перемещение пропускают ссылки; перенос целой папки
  на новый путь может использовать переименование. Проверка блокирующих удаление
  объектов до начала и сообщение об уже удалённых элементах при частичном сбое.
- Git, MIT, CHANGELOG, версия 0.2.0 и локальные теги v0.1.0/v0.2.0.
- Workflow тестов Windows/Ubuntu, сборки архивов и публикации по тегу.
- Скрипты установки/удаления Windows, установки Linux, сборки .deb и проверки .NET 10.

## Приоритет 1 — стабилизация существующей версии

- Выполнено: устранены тайм-ауты UI-тестов при `WindowTests.Open`; результаты выше.
- Выполнено: проверены ошибки задания/обновления панелей, отмена при конфликте и вложенном
  переименовании, очистка и остановка очереди. Добавление после остановки отклоняется,
  ресурсы отмены освобождаются. Окно не закрывается во время переноса; после отмены через Esc
  закрывается. Исправления закреплены тестами ядра и headless UI на обеих платформах.
- Выполнено локально: `publish.yml` вызывает общий `test.yml` из того же коммита.
  Обе сборки требуют успешных тестов Windows/Ubuntu, включая теги и ручной запуск;
  релиз зависит от обеих сборок. PR запускают тот же набор тестов самостоятельно.
  Право записи оставлено только заданию создания релиза. Проверка в GitHub Actions — после push.
- Выполнено локально: деинсталлятор удаляет только файлы из манифеста установки.
  Каталог с посторонним `DC.exe`, корень диска и профиль пользователя не принимаются.
  Ярлык удаляется, только если указывает на эту копию.

## Приоритет 2 — довести распространение

- Выполнено локально: самопроверки установки, обновления и удаления. Отсутствующий runtime
  и бинарник другой архитектуры отклоняются по заголовку PE/ELF, а не по имени каталога.
  Нестандартный x64-runtime принимается, в том числе через `DOTNET_ROOT`.
  Чистая машина здесь не поднималась: это проверка сценариев скриптами.
- Выполнено локально: пользовательская установка и `.deb` добавляют `dockcommander.desktop`
  и значок в меню приложений.
- Выполнено локально: везде требуется Microsoft.NETCore.App 10 x64. Desktop Runtime указан
  как способ получить этот framework на Windows, а `dotnet-runtime-10.0` — на Debian/Ubuntu.
- Решение: отдельный графический установщик Windows не делаем. PowerShell-скрипт остаётся
  установщиком и не встраивает .NET.

## Приоритет 3 — ручная проверка рабочего стола

- Обычные Debian/Ubuntu, не только WSL: окна, масштабирование, обе темы,
  X11/XWayland, конфликтующие сочетания, мышь и внешнее перетаскивание.

## Приоритет 4 — Remote UI и подготовка сетевых провайдеров

Следующий крупный этап после стабилизации локального файлового менеджера — удалённые файловые системы.

### Remote UI

Каждая из двух панелей должна иметь собственный переключатель:

`Local | Remote`

Активная панель визуально подсвечивается существующим способом. Отдельные концепции left-active, right-active и аналогичные варианты не нужны: активность панели и её режим Local/Remote — независимые состояния.

При выборе Local панель работает как сейчас.

При выборе Remote на первом этапе показывается только интерфейс управления подключениями без реального сетевого соединения.

Верхняя часть Remote-панели:

- поле `Search connections...`
- кнопка `Add connection`

Ниже — список сохранённых соединений.

Формат строки соединения:

```text
Production
SFTP · server.example.com:22                         Edit   Connect

Old NAS
FTP · 192.168.1.20:21                                Edit   Connect

Cloud
WebDAV · cloud.example.com                           Edit   Connect
```

Требования к отображению:

- имя соединения — основной текст;
- под ним меньшим и менее акцентным текстом отображаются протокол и адрес;
- справа находятся действия Edit и Connect;
- весь интерфейс на английском;
- без отдельных цветных badges протокола;
- Remote UI должен оставаться частью обычного FilePane, а не отдельным окном или отдельным файловым менеджером.

На этом этапе Connect может показывать заглушку, например: `Remote connections are not implemented yet.`

Цель первого этапа — проверить UX переключения Local / Remote, внешний вид списка, поиск и управление профилями до реализации сетевых протоколов.

### Модель подключения

Подготовить нейтральную модель профиля соединения, не привязанную к одному протоколу.

Базовые поля:

- Name
- Protocol
- Host
- Port
- Username
- Initial path
- Authentication

Конкретные провайдеры позже могут добавлять собственные параметры.

Секреты, пароли и passphrase не должны храниться открытым текстом в обычном `settings.json`.

### Cross-provider transfers

Перед первым рабочим сетевым провайдером подготовить файловые операции к переносу данных между разными `IFileSystemProvider`.

Целевые сценарии:

- Local → Remote
- Remote → Local
- Remote A → Remote B

Очередь, progress, cancellation и conflict handling должны оставаться общими и не зависеть от конкретного протокола.

Архитектурно FilePane должен уметь менять текущий provider без создания отдельного UI.

### Первый сетевой провайдер

Первым полноценным сетевым провайдером сделать SFTP.

Он должен использовать существующую модель панели и файловых операций:

- list
- read
- write
- create directory
- rename
- delete
- upload/download через общую очередь
- cancellation
- conflict handling
- обработка disconnect/network errors

После проверки архитектуры на SFTP последовательно добавить:

- FTP / FTPS
- WebDAV

Другие варианты, включая PowerShell Remoting, рассматривать позже отдельным решением.

Отдельный filesystem-provider поверх SSH shell не планируется: файловый доступ через SSH должен использовать SFTP.

### Принцип

Remote не должен превращаться в отдельный FTP/SFTP-клиент внутри DockCommander.

Основная модель проекта: каждая панель — независимый файловый provider.

Одна панель может быть Local, другая Remote, либо обе могут использовать разные Remote-подключения.

Пример:

```text
C:\Projects\site               SFTP · Production
                               /var/www/site
```

Обычные действия DockCommander (F5, F6, selection, queue, progress, cancel, conflicts) должны максимально одинаково работать между любыми поддерживаемыми provider.

## Позже, по отдельному решению

- Перетаскивание из DockCommander в другие приложения и внутри одной панели.
- Закладки пользователя и дополнительные удобства навигации.
- Архивы как возможный provider для навигации внутри архива.

Отдельный встроенный архиватор, image viewer и другие специализированные просмотрщики сейчас не планируются. Архивирование и подобные операции по возможности передаются ОС и установленным приложениям, включая системное Shell menu.

Очередь, общий прогресс, Linux-корзина и базовые установщики больше не являются
будущими задачами — следующий этап для них именно проверка и доработка.
